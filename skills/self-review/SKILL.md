# Self-Review

PRを出す前に自分の変更を5観点でレビューし、問題点のみを指摘する。

## Step 1: 差分の取得

引数があれば差分対象として使う（例: `HEAD~1`、`feature/my-branch`）。引数がgit参照ではなくファイルパス（git管理外を含む）なら、そのファイル全体をレビュー対象とし、Step 2以降の観点を内容に合わせて読み替える。

引数がなければデフォルトブランチを自動検出する。検出できなければ `main`、それも無ければ `dev` を試みる。

```bash
git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's|refs/remotes/origin/||'
git diff origin/<default>...HEAD
```

基点はローカル参照ではなくリモート追跡参照（`origin/<default>`）を優先し、必要なら先に fetch する（ローカルのデフォルトブランチが古いと無関係な差分が混ざるため）。

- 差分が空でも未コミットの変更（未追跡ファイルを含む）があれば、それを対象とする
- 差分も未コミットの変更も空ならその旨を伝えて終了する。ただしユーザーが全体レビューを求めている場合は、空ツリー（`git hash-object -t tree /dev/null`）を基点にリポジトリ全体を対象とする
- 同一ブランチへの再レビュー時も全差分を対象とするが、前回レビュー以降の変更を重点的に確認する

## Step 2: プロジェクト規約ドキュメントの特定

全ドキュメントを読むと時間とコンテキストを浪費するので、規約に関連するファイルのみを絞り込む。

1. `CLAUDE.md` と `.claude/CLAUDE.md` を読む（規約の主要な情報源）。プロジェクト固有のスキル（`.claude/skills/*/SKILL.md`）があれば、差分に関連するものも合わせて読む（コード変更がスキルに書かれた規約・記法と同期しているか確認するため）
2. `docs/` があれば、ファイル名（`*guideline*`, `*convention*`, `*architecture*`, `*style*` 等）と本文のキーワード（「禁止」「規約」「ルール」「must」「should」）で規約に関わるファイルを絞り込む。無ければ飛ばす
3. **差分で変更した関数名・環境変数名・設定キーなど（改名・削除した旧名も含む）の識別子で、リポジトリ全体（Markdown だけでなく `tests/` を含むコードのコメント・docstring も）を Grep し、その挙動を説明した記述が古くなっていないか特定する**（例: 挙動が条件分岐するようになったのに「常にXする」のまま、テストが変更前の前提を根拠として語ったまま）。識別子が変わらず挙動だけ変えた場合や散文（「〜するツールです」等）は Grep で拾えないため、**変更箇所と同じ階層の README・ヘッダーコメント・テスト見出しは、検索に当たらなくても直接開く**。これは観点1「取り残し」と観点4「ドキュメント」の判定に使う
4. 上記で特定したファイルのみを読む

## Step 3: 5観点でのレビュー

差分と規約ドキュメントを照らし合わせて問題を探す。「問題がない」項目は一切出力しない。
太字は見落としやすい項目。差分に該当がなければ飛ばしてよい。

### 1. コード品質
- 基本: 命名の意図、単一責務（50行超は注意）、コメントアウト・デバッグコードの残骸、明白なコピペ重複（踏み込んだ簡潔化は `simplify` スキルに委ねる）。追加・移動したフィールドが既存の同種フィールドと同じ階層にあるか。UI変更時はコントラストがWCAG AAを満たすか（通常4.5:1、18.66px太字/24px以上は3:1、背景は最も明るい箇所で判定）
- **ロジックの正確性**: パス計算・API引数・変換順序。`None` や省略時デフォルトが実際に何をするか（既定値が多層なら、実際に値を渡す呼び出し元の層まで遡る）。新規に使うライブラリのオプションは実装で意味論を確かめる（mock と本番で挙動が違うと、テストが通っても本番だけ壊れる）。allowlist・パターンマッチ・enum分岐は、実際にそこへ流れる値（`.env`・設定・シード・定数）を列挙して1件ずつ判定を通す。一時ファイル・接続・課金対象が失敗経路でも解放/返却されるか（`with` 優先）
- **取り残し**: 旧実装の持っていた保護（スロットル・ガード・早期return等）を落としていないか。旧コードが何を防いでいたかを1つずつ新コードで確認する。コメント・UI文字列・ログが変更前の前提を語ったまま残っていないか（認証を足したのに「認証なし」等）

### 2. テスト
- 変更した機能のテスト、追加コードパスのエッジケース、プロジェクトのテスト規約（モックの使い方・テストの独立性）
- **回帰を防ぐテストは、実装を壊すと本当に落ちるかを確かめる**（テストやコメントに挙げた例の値が、想定した失敗を実際に起こすか）

### 3. セキュリティ
- システム境界での入力検証、認証・認可のチェック漏れ、シークレットのハードコード、注入（SQL・XSS・コマンド）

### 4. ドキュメント
- 新コンセプト・コンポーネント・重要な設計変更に対応する更新。APIならOpenAPI、アーキテクチャ決定ならADR
- **決定の上書き**: 既存の設計記録の決定を覆したら覆された側にも追記する（古い記録が単体で現行仕様に見えるため）

### 5. プロジェクト規約
- Step 2 で読んだ規約への違反、インポート配置、エラーハンドリングのパターン、禁止された抑制コメント（型・lintのinline ignore）、サービス名・接続先・環境依存値のハードコード
- **プロトコル契約**: 応答経路（SSE等）を変えたら、正常系・エラー系すべての終了パスが仕様と既存の慣習（エラーイベント後にも終了イベント、ログ→イベント→終了の順序）に従うか
- **依存差分**: 意図外のパッケージ・新規間接依存の混入、供給元ルール（公開日制限・レジストリ制約）への全依存（間接含む）の適合

## Step 4: 結果の出力

問題が見つかった場合のみ、以下の形式で出力する:

```
### [番号] [観点]（深刻度: 高/中/低） — [問題の概要]
場所: `ファイル名:行番号`（特定できる場合。複数ファイルにまたがる不整合は全箇所を列挙する）
問題: 何が問題か
失敗シナリオ: 具体的にどんな入力・状態のとき、どう誤動作・クラッシュするか（裏を取れたものだけ断定し、取れなければ推測と明示する）
提案: どう直すか（具体的なコード例があれば示す）
```

見出しにするのは、日本語では `**太字**` が全角約物に隣接すると描画されないため。

問題がなければ「レビュー完了: 問題は見つかりませんでした」と伝えて終了する。

## Step 5: 修正の確認

問題が1件以上あった場合、一度だけ聞く:

> 修正する問題の番号を教えてください（例: 1,3,5 / all / none）

指摘一覧と同一ターンで `AskUserQuestion` を呼ばない（ダイアログが一覧表示に被さり、指摘が読まれる前に選択を迫るため）。一覧を提示したターンではテキストで質問し、`AskUserQuestion` は一覧を前のターンで提示済みの場合のみ使う。

指定された番号の問題を修正する（Bash・Edit ツールはユーザー確認が求められる）。`none` またはスキップ指示があればそのまま終了する。

自律実行（/goal やヘッドレス実行等）でユーザーの応答を得られない場合は、`all` が選択されたものとして全件修正し、最終報告に指摘内容と修正内容を明記する。
